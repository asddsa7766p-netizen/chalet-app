### lib/presentation/screens/owner/chalet_pricing_screen.dart

- **الوظيفة:** الشاشة التي تجمع كل وحدة "تسعير الشاليه" (المراجَعة بهذه الدفعة) بمكان واحد: لوحة السعر الفعلي، أنواع الإقامة (تفعيل/أوقات/سعر احتياطي)، التسعير الأسبوعي (تبويبات لكل نوع)، وأسعار التواريخ الخاصة. **1551 سطراً — أكبر ملف بهذه الدفعة، ومن أكثر شاشات المشروع بأكمله نضجاً هندسياً وحرصاً على تجربة المستخدم.**

- **الشرح التفصيلي:**
  - **`_PriceField`**: يفصل بدقة بين النص المكتوب حالياً (`ctrl.text`)، القيمة المحفوظة (`savedValue`/`savedText`)، وهل الحقل "متّسخ" (`dirty`) أم لا. `draftValue` يتعامل بأمان مع نص غير صالح أثناء الكتابة (لا يُفسد لوحة المعاينة الحية بقيمة `null` مؤقتة، يُبقي آخر قيمة محفوظة بدلاً منها) — تعليق يوثّح هذا صراحة.
  - **حماية فقدان التعديلات (Unsaved changes guard) — الأكثر شمولاً بكل المشروع**: `PopScope(canPop: dirty == 0 && !_savingAll, onPopInvokedWithResult: ...)` يمنع الخروج بوجود تعديلات غير محفوظة، ويعرض حواراً بثلاثة خيارات (حفظ وخروج / تجاهل / البقاء). نفس الحماية مُطبَّقة أيضاً عند السحب للتحديث (`_onRefresh`) وعند إيقاف نوع إقامة له تعديلات معلَّقة (`_toggleStayType`). **هذا النمط غائب تماماً عن معظم شاشات التعديل الأخرى بالمشروع** (لم أجده بـbooking_screen.dart ولا owner_add/edit_chalet_screen حتى الآن).
  - **`_saveAll()`**: يحفظ كل الحقول المتّسخة (بطاقات الأنواع + كل أسعار الأيام لكل التبويبات المرئية)، ويعدّ النجاح/الفشل **بدقة لكل حقل على حدة** (`ok`/`failed`)، ويقرر رسالة نهائية تعكس النتيجة الفعلية بدل افتراض "كله نجح" أو "كله فشل".
  - تتبّع "اتّساخ" متعدد المستويات (`_cardDirty`, `_dirtyWeekdays`, `_typeDraftCount`, `_dirtyCount`) يغذّي: نقاط صغيرة على تبويبات فيها مسودة غير محفوظة، حدوداً ملوّنة وكلمة "لم يُحفظ" لكل حقل متّسخ، وزر "حفظ" مفعَّل/معطَّل بدقة لكل بطاقة.
  - **إمكانية وصول واستجابة نصية حقيقية ومُختبَرة فعلياً**: `_timeTile` يتحقق من `MediaQuery.textScalerOf(context).scale(1) > 1.3` (نص كبير/إعدادات إتاحة) ويبدّل من `Row` إلى `Column` لتفادي الفيض — و`_typeTab` (تعليق سطر 1308-1310) يوثّق صراحة أن التبويبات استُبدلت من `ChoiceChip` القياسية لأن "ارتفاعها الثابت يقصّ النص عند تكبير مقاييس الخط، **لوحظ بخط التطبيق الفعلي على الويب**" — إصلاحان لعطل فيض نص **مُلاحَظ فعلياً** (وليس نظرياً) بمقاسات خط كبيرة.
  - `_weekdayHint`: يعرض تلميحاً حياً وصحيحاً مثل "فارغ ← ₪150 من «عام»" — يحسب فعلياً (عبر `PricingSnapshot.withoutWeekday` من [pricing_preview.dart](pricing_preview.md)) القيمة التي سيرجع إليها الحقل لو أُفرغ، بدل نص عام.

- **الاعتماديات:** `pricing_service.dart`, `base_price_notice.dart`, `effective_price_panel.dart`, `pricing_data_source.dart`, `pricing_preview.dart`. **من يستخدمه:** على الأرجح [owner_chalets_screen.dart](owner_chalets_screen.md) (زر إدارة تسعير شاليه).

- **التعامل مع Supabase:** عبر `PricingDataSource` حصراً (لا اتصال مباشر) — `chalet_stay_types` (upsert)، `chalet_weekday_prices` (set/clear)، `chalet_date_prices` (set/delete).

- **نقاط القوة:**
  - **الأكثر حرصاً بكل المشروع على عدم فقدان عمل المستخدم غير المحفوظ** — حوار خروج بثلاثة خيارات، حماية عند التحديث، حماية عند إيقاف نوع.
  - إصلاحا فيض نص موثَّقان بأدلة ملاحظة فعلية (وليس افتراضاً) — وعي حقيقي بإمكانية الوصول ومقاسات الخط الكبيرة.
  - تتبّع دقيق ومتعدد المستويات لحالة "غير محفوظ"، مع رسائل نتيجة حفظ دفعي تعكس النجاح/الفشل الفعلي لكل عنصر لا افتراضاً عاماً.
  - إدارة موارد شاملة تقريباً (دزينات من `TextEditingController` تُنشأ وتُتخلَّص منها جميعاً بـ`dispose()` عبر `_allFields`).
  - تحميل متوازٍ (`Future.wait`) لكل البيانات اللازمة (أنواع + أسعار أيام لكل الأنواع + تواريخ خاصة) بدل تسلسل نداءات شبكة.

- **الأخطاء والمخاطر المحتملة:**
  - 🟠 **متوسطة (سطر 60-61، 657 — وبالامتداد كل حقل سعر بالشاشة) — نفس فجوة تطبيع الأرقام العربية-الهندية المذكورة بمراجعة [chalet_edit_validation.dart](chalet_edit_validation.md)، مؤكَّدة هنا فعلياً بأهم شاشة أسعار بالتطبيق:**
    ```dart
    double? get _parsed {
      final v = double.tryParse(text);   // ⚠️ بدون تطبيع أرقام عربية-هندية أولاً
      ...
    }
    ```
    و`_addDateOverride`: `double.tryParse(priceController.text.trim())` — نفس الأمر. **كل حقل سعر بهذه الشاشة بالكامل** (السعر الاحتياطي، أسعار الأيام السبعة لكل تبويب، سعر التاريخ الخاص) عرضة لنفس المشكلة: مالك يكتب سعراً بأرقام عربية-هندية (شائع على لوحات مفاتيح عربية، وأحياناً افتراضي بإعدادات النظام العربية) سيُرفَض بصمت كـ"سعر غير صحيح" رغم أنه رقم صحيح تماماً من منظوره. `ChaletEditValidation.normalizeDigits` (بملف آخر بنفس المجلد!) تحل بالضبط هذه المشكلة لكنها غير مُستوردة/مُستخدمة هنا.
  - 🟡 **بسيطة (سطر 601-602، `_addDateOverride`) — تسريب Controller حقيقي:** `priceController`/`noteController` يُنشآن محلياً داخل الدالة ويُستخدَمان بالـ`AlertDialog`، **لكن لا يُستدعى `.dispose()` عليهما أبداً** (لا بعد الإغلاق بنجاح، ولا بعد الإلغاء). كل عملية "إضافة سعر خاص" تُنشئ Controller-ين جديدين يبقيان بالذاكرة للأبد. تسريب صغير الأثر فردياً، لكنه حقيقي ويتكرر مع كل استخدام لهذه الميزة على مدى عمر الشاشة.
  - 🟡 **بسيطة (سطر 688-702، `_deleteDateOverride`) — الفجوة الوحيدة من نوعها بملف حريص جداً بهذا الخصوص في كل مكان آخر:**
    ```dart
    Future<void> _deleteDateOverride(ChaletDatePrice item) async {
      try {
        await _ds.deleteDateOverride(...);
        setState(() { ... });   // ⚠️ بدون فحص mounted، بخلاف كل دالة أخرى بالملف
        ...
    ```
    كل دالة async أخرى بهذا الملف تتحقق بعناية من `mounted` قبل `setState` بعد `await` — هذه الدالة تحديداً فقط لا تفعل (`_showSnack` نفسها محمية داخلياً بفحص `mounted` منفصل، فالمخاطرة الفعلية تنحصر بسطر `setState` هذا تحديداً).
  - 🟡 **بسيطة:** `_deleteDateOverride` بلا حارس مثل `_savingDateOverride` (المستخدَم بـ`_addDateOverride`) — ضغط مزدوج سريع على حذف نفس العنصر قد يرسل نداءين متزامنين (أثر محدود: الثاني على الأرجح لا يجد شيئاً ليحذفه، والخطأ يُلتقَط ويُعرض كرسالة فقط).

- **اقتراح الإصلاح:**
  - استيراد واستخدام `ChaletEditValidation.normalizeDigits`/`parseNumber` (أو نقلها لمكان مشترك، راجع توصية [chalet_edit_validation.md](chalet_edit_validation.md)) بكل مكان يُستدعى فيه `double.tryParse`/`double.parse` بهذا الملف، تحديداً `_PriceField._parsed` و`_addDateOverride`.
  - إضافة `priceController.dispose()`/`noteController.dispose()` بعد إغلاق حوار `_addDateOverride` (بعد `showDialog` مباشرة، بغض النظر عن النتيجة).
  - إضافة `if (!mounted) return;` قبل `setState` بـ`_deleteDateOverride`، بنفس نمط بقية الدوال.
