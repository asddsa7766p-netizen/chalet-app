### lib/presentation/screens/owner/owner_add_chalet_screen.dart

- **الوظيفة:** معالج (wizard) بـ4 خطوات لإضافة شاليه جديد: معلومات أساسية، صور/فيديو، مميزات، أسعار/توافر — ثم حفظ نهائي يُنشئ الشاليه ويحاول تفعيل وضع "مالك" للمستخدم. **1350 سطراً.**

- **الشرح التفصيلي:**
  - `_saveAll()`: يتحقق من صحة الخطوتين 1 و4 (والصور)، يبني الحمولة (`_buildChaletPayload`)، يستدعي `ChaletService.instance.createOrUpdateChaletWithImages(isEditing: false, ...)` (المسار الحقيقي لرفع الصور وإنشاء الصف — راجع [services.dart](../../../data/services/services.md))، ثم **إصلاح موثَّق بعناية فائقة (سطر 423-451)**: يستدعي `AuthService.instance.becomeOwner()` ويتحقق فعلياً من قيمته المرجعة (بدل تجاهلها كما كانت سابقاً). السبب: أي شاليه جديد يُنشأ دائماً بـ`is_approved=false` (بانتظار مراجعة الإدارة)، وشرط `become_owner()` بالباك إند يتطلب شاليهاً معتمداً واحداً على الأقل — فكانت النسخة القديمة تعرض "نجاح" وتنتقل مباشرة لـ`/owner-dashboard` رغم أن الدور لم يتغيّر فعلياً، فيطرده حارس الراوتر (`isHost()`) فوراً وكأن كل شيء اختفى. الإصلاح الحالي يميّز الحالتين (أصبح مالكاً فعلاً ← لوحة التحكم؛ الشاليه محفوظ لكن بانتظار موافقة ← رسالة واضحة + الرئيسية) ويستدعي `ref.invalidate(profileProvider)` لمزامنة الحالة فوراً.
  - `_confirmLeaveIfDirty`/`PopScope`: يمنع الخروج العرضي من الشاشة بوجود بيانات مكتوبة، بحوار تأكيد.
  - إصلاحا "BoxConstraints forces an infinite width" موثَّقان بدقة (سطر 649-656، زر تحديد الموقع؛ وسطر 1143-1145، زر "حفظ كمسودة") — **نفس عطل الثيم العام** (`OutlinedButtonTheme` يفرض `minimumSize: Size(double.infinity, 52)` على زر غير مرن داخل `Row`) المُلاحَظ ومُصلَح أيضاً بـ[search_screen.dart](../search/search_screen.md) — نمط عطل متكرر بالمشروع، لكنه دائماً يُكتشف ويُصلَح بنفس الطريقة الصحيحة (`minimumSize: Size.zero`/تحديد عرض صريح).

- **الاعتماديات:** `image_picker`, `services.dart`, `location_service.dart`, `models.dart`, `chalet_model.dart`, `common_widgets.dart`, `profile_provider.dart`. **من يستخدمه:** [app_router.dart](../../../core/router/app_router.md) (مسار `/owner-add-chalet`، **بدون تمرير أي `chalet` — مؤكَّد بمراجعة app_router.dart** — راجع الملاحظة أدناه).

- **التعامل مع Supabase:** عبر `ChaletService.createOrUpdateChaletWithImages` (إدراج `chalets` + رفع صور)، `AuthService.becomeOwner` (RPC).

- **نقاط القوة:**
  - إصلاح `becomeOwner()` (أعلاه) مثال ممتاز على تتبع عطل معقّد عابر لعدة طبقات (RPC + حارس راوتر + رسالة واجهة) لجذره الحقيقي بدل معالجة عرضية.
  - معالجة أخطاء دقيقة لكل صورة على حدة بـ`_pickImages` (ملف واحد فاشل لا يمنع البقية) — نفس جودة `ChaletService.uploadChaletImages`.
  - حماية من فقدان البيانات عند الخروج العرضي (رغم كونها أضيق نطاقاً من [chalet_pricing_screen.dart](chalet_pricing_screen.md) — راجع أدناه).

- **الأخطاء والمخاطر المحتملة:**
  - 🟠 **متوسطة (سطر 272-309) — دالة `_uploadNewImages` معطوبة بالكامل وميتة فعلياً (مؤكَّد بقراءة الكود مباشرة، ويتّفق مع تحذيرات `flutter analyze` القديمة):**
    ```dart
    Future<List<String>> _uploadNewImages(String chaletId) async {
      final uploadedUrls = <String>[];
      for (int i = 0; i < _newImages.length; i++) {
        ...
        final contentType = ...;  // يُحسَب ولا يُستخدَم أبداً
        final fileName = ...;      // يُحسَب ولا يُستخدَم أبداً
        try {
          final bytes = ...;
          if (bytes.isEmpty) continue;
        } catch (_) { continue; }
        // ⚠️ لا يوجد أي استدعاء رفع فعلي هنا — الحلقة تنتهي بدون فعل شيء
      }
      return uploadedUrls;  // فارغة دائماً، مهما كانت الصور المُمرَّرة
    }
    ```
    هذه الدالة **لا تفعل شيئاً فعلياً على الإطلاق** — تحسب متغيرات (`contentType`, `fileName`) لا تُستخدَم، وتنتهي كل حلقة بـ`continue` بدون أي نداء رفع حقيقي، فتُرجع قائمة فارغة دائماً. **ولا تُستدعى من أي مكان بالملف أصلاً** (الرفع الفعلي يحدث حصراً عبر `ChaletService.createOrUpdateChaletWithImages` باستدعاء منفصل بـ`_saveAll`) — كود ميت ومعطوب بنفس الوقت، على الأرجح بقايا محاولة سابقة استُبدلت بالمسار الحالي (`ChaletService`) دون حذفها.
  - 🟠 **متوسطة (سطر 951-954 مقابل `_buildBottomBar`) — لا وسيلة للرجوع خطوة للخلف بالمعالج رغم وجود الدالة اللازمة لذلك جاهزة وصحيحة:** `_handleStepCancel()` (تُرجع `_currentStep` خطوة للخلف) **موجودة ومطبَّقة بشكل صحيح لكن غير مربوطة بأي زر بالواجهة** — `_buildBottomBar` يحتوي فقط زري "التالي/حفظ الشاليه" و"حفظ كمسودة"، بلا أي زر "السابق". **النتيجة الفعلية**: مالك وصل للخطوة 3 أو 4 واكتشف أنه أخطأ ببيانات الخطوة 1 **لا يملك وسيلة للرجوع وتصحيحها** سوى مغادرة الشاشة بالكامل (بتأكيد فقدان البيانات) والبدء من جديد بمعالج 4 خطوات كاملاً — فجوة استخدام حقيقية بحل جاهز غير مُفعَّل.
  - 🟡 **بسيطة (سطر 18-21, 79, 91-99) — كود "وضع تعديل" متبقٍ وغير قابل للوصول فعلياً:** الـ widget يقبل `chalet` اختيارية، ويحتوي `_editingChaletId` (يبقى `null` دائماً — لا مكان بالملف يُسنِد له قيمة)، وإن وصل `widget.chalet` غير فارغ يعرض تحذيراً صريحاً "تعديل شاليه موجود غير مدعوم حاليًا". **تأكدت بمراجعة [app_router.dart](../../../core/router/app_router.md)** أن مسار `/owner-add-chalet` لا يُمرِّر `chalet` أبداً — فهذا المسار بأكمله غير قابل للوصول عملياً حالياً (التعديل الفعلي يتم عبر [owner_edit_chalet_screen.dart](owner_edit_chalet_screen.md) المنفصل). بقايا تصميم سابق قبل فصل شاشتي الإضافة/التعديل.
  - 🟡 **بسيطة (سطر 350، 363) — نفس فجوة تطبيع الأرقام العربية-الهندية** المذكورة بمراجعة [chalet_edit_validation.dart](chalet_edit_validation.md)/[chalet_pricing_screen.dart](chalet_pricing_screen.md): `double.tryParse(_pricePerNightCtrl.text.trim())`/`int.tryParse(_maxGuestsCtrl.text.trim())` بلا تطبيع أولاً — مالك يكتب السعر/عدد الضيوف بأرقام عربية-هندية سيُرفَض حقله بصمت (`?? 0`/`?? 1` تُطبَّق قيمة افتراضية خاطئة بدل رسالة خطأ توضّح السبب الفعلي، وهذا أخطر قليلاً من رسالة خطأ عادية: **سعر شاليه جديد قد يُحفَظ فعلياً كـ0 دون أن ينتبه المالك**، لأن `validator` بالنموذج (`double.tryParse(v?.trim() ?? '') <= 0`) سيرفض القيمة فعلاً بنفس طريقة الفشل الصامت — يحتاج التأكد: **يحتاج تحقق دقيق إضافي** هل الـ`validator` بالفعل يمنع المتابعة بهذه الحالة (يبدو أنه يفعل، لأن نفس منطق `tryParse` الفاشل يُرجع `null` فيرفضه الـ`validator` أيضاً) — الأثر الأرجح إذاً "خطأ تحقق مربك" أكثر من "حفظ سعر خاطئ صامت"، لكنه يستحق نفس الإصلاح المقترح بالملفات الأخرى بغض النظر.
  - 🟡 **بسيطة (سطر 29-30، 1196، 1253) — `_gold` ثابت غير مُستخدَم، بينما نفس قيمته مكرَّرة يدوياً بمكانين آخرين:** `static const Color _gold = Color(0xFFC9A24B);` مُعرَّف لكن غير مُستخدَم أبداً (مؤكَّد بالبحث بالملف)؛ بدلاً منه `Color(0xFFC9A24B)` مكتوبة حرفياً مرتين منفصلتين (`_CoverImageBox`, `_DottedBorderPainter`) — لو احتاج أحدهما تغييراً لوحده مستقبلاً، لا رابط بينهما يمنع الانحراف.
  - 🟡 **بسيطة (سطر 116-120) — تحقق "هل يوجد بيانات غير محفوظة" أضيق نطاقاً من الحماية المكافئة بملفات أخرى:** `_confirmLeaveIfDirty` يفحص فقط `_nameCtrl`/`_descCtrl`/`_newImages` — لا يفحص السعر، المدينة، المرافق المختارة، عدد الغرف/الحمامات، أو الفيديو. مالك عدّل هذه الحقول فقط (دون كتابة اسم/وصف أو اختيار صور) يمكنه الخروج بلا أي تحذير رغم فقدان تعديلاته فعلياً.

- **اقتراح الإصلاح:**
  - حذف `_uploadNewImages` بالكامل (كود ميت ومعطوب، غير مُستخدَم).
  - ربط `_handleStepCancel` بزر "السابق" فعلي بـ`_buildBottomBar` (يظهر فقط لو `_currentStep > 0`)، بنفس تصميم أزرار "التالي"/"حفظ كمسودة" الحاليين.
  - حذف `chalet`/`_editingChaletId` وكل الكود المرتبط بهما بما أن التعديل انتقل فعلياً لملف منفصل، أو توضيح بتعليق أنها لا تزال مقصودة لاستخدام مستقبلي محدد.
  - توسيع فحص `_confirmLeaveIfDirty` ليشمل كل الحقول القابلة للتعديل، أو (أبسط) مقارنة الحالة الحالية بالكامل بحالة أولية محفوظة.
  - تطبيق `normalizeDigits` (من [chalet_edit_validation.dart](chalet_edit_validation.md)) على حقلي السعر وعدد الضيوف.
